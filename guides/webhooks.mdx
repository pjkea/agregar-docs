title: Webhooks
description: "Get pushed events instead of polling"
---

Validar pushes events to your HTTPS endpoint as they happen. Each institution registers its own URLs; there is no shared configuration and no polling required.

---

## Register an endpoint

```bash
curl -X POST https://monitor.agregartech.com/api/v1/webhooks/endpoints \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://your-system.example.com/validar-hook",
    "events": ["TRANSACTION_SCORED", "ALERT_GENERATED"]
  }'
```

```json
{
  "id": "6e1a1542-eb16-4721-8c66-3f81ee10389d",
  "url": "https://your-system.example.com/validar-hook",
  "events": ["TRANSACTION_SCORED", "ALERT_GENERATED"],
  "is_active": true,
  "secret": "4ca15b7fecddc2590ec44c5b178249a5..."
}
```

<Warning>
  `secret` is returned **once**, at creation. Store it now — you need it to verify signatures, and it cannot be retrieved later.
</Warning>

## Events

| Event | Fires when |
|---|---|
| `TRANSACTION_SCORED` | A transaction finishes scoring |
| `ALERT_GENERATED` | An alert is raised |
| `CASE_CREATED` | A case is opened |
| `CASE_ESCALATED` | A case is escalated |
| `SLA_BREACH` | A case passes its SLA deadline |
| `STR_FILED` | An STR is filed |
| `CTR_FILED` | A CTR is filed |

Subscribing to an unlisted value returns `422` naming the valid set.

## What you receive

Every delivery is a POST with three headers:

| Header | Contents |
|---|---|
| `X-TMS-Signature` | `sha256=<hex digest>` |
| `X-TMS-Event` | The event type |
| `X-TMS-Delivery` | Unique delivery id, for idempotency |

The body is the same envelope for every event, with an event-specific `data`:

```json
{
  "event": "ALERT_GENERATED",
  "timestamp": "2026-09-11T09:30:00Z",
  "data": {
    "alert_id": "ALT-931009009142",
    "transaction_id": "TXN-DACB711B5551",
    "customer_id": "CUST001",
    "risk_score": 185,
    "priority": "IMMEDIATE",
    "status": "OPEN"
  }
}
```

Use `POST /webhooks/test` to receive a real delivery of any event type against your endpoint, so you can confirm shape and signature before going live.

## Verify the signature

Always verify before acting. The signature is an HMAC-SHA256 of the **raw request body** using your endpoint secret.

```python
import hmac, hashlib

def valid(raw_body: bytes, header: str, secret: str) -> bool:
    if not header.startswith("sha256="):
        return False
    expected = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header[len("sha256="):])
```

Two things that will bite you: compute the HMAC over the **raw bytes** you received, not over a re-serialised object, and compare with `compare_digest` rather than `==`.

## Delivery and retries

Respond `2xx` within **10 seconds**. Anything else is a failure and is retried:

| Attempt | Wait |
|---|---|
| 1 | immediate |
| 2 | 30 seconds |
| 3 | 5 minutes |
| 4 | 30 minutes |
| 5 | 2 hours |

After 5 failed attempts the delivery is marked permanently failed and is not retried.

Deliveries are **at-least-once**: a slow `2xx` can still be retried, so the same event may arrive twice. Deduplicate on `X-TMS-Delivery`.

Do your processing after responding. Acknowledge first, work second.

## When something is missing

```bash
curl "https://monitor.agregartech.com/api/v1/webhooks/endpoints/{endpoint_id}/deliveries" \
  -H "X-API-Key: $API_KEY"
```

Shows each attempt with its response code and body, which is usually enough to tell a TLS problem from a 500 in your handler.

Webhooks are a convenience, not the system of record. Anything delivered by webhook can also be read from [`/alerts`](/api-reference/alerts) and [`/cases`](/api-reference/cases).

## Manage

| Endpoint | Purpose |
|---|---|
| `GET /webhooks/endpoints` | List yours |
| `PATCH /webhooks/endpoints/{id}` | Change URL or event list |
| `DELETE /webhooks/endpoints/{id}` | Remove (returns `204`) |
