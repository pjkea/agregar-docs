Every endpoint except `GET /health` requires authentication. There are two credentials and **they are not interchangeable** — read the table below before you start.

<Tip>
  Building an integration? Do it in [Sandbox](/guides/sandbox) first — the same credentials and endpoints, running the real engine, with nothing reaching your live reporting or a regulator.
</Tip>

---

## Which credential for which endpoint

<Warning>
  An API key does **not** work on every endpoint. Reading transactions, cases, customers or reports requires a Bearer token. Using an API key there returns `401 Could not validate credentials`.
</Warning>

| Endpoint | API key | Bearer token |
|---|:---:|:---:|
| `POST /ingestion/transaction` | yes | yes |
| `POST /ingestion/batch` | yes | yes |
| `POST /ingestion/validate` | yes | yes |
| `GET /ingestion/batch/{id}/status` | yes | yes |
| `GET /alerts`, `GET /alerts/{id}` | yes | yes |
| `GET /webhooks/endpoints` (and writes) | yes | yes |
| `GET /health` | no auth | no auth |
| `GET /transactions` | **no** | yes |
| `GET /customers/...` | **no** | yes |
| `GET /cases` | **no** | yes |
| `GET /str-reports`, `GET /ctr-reports` | **no** | yes |

In short: **push with an API key, read back with a token.** A typical integration uses both — the API key in your core banking system, a token in whatever your compliance team uses to review.

## API key

Pass the raw key in `X-API-Key`:

```bash
curl -X POST https://monitor.agregartech.com/api/v1/ingestion/transaction \
  -H "X-API-Key: your_api_key_here" \
  -H "Content-Type: application/json" \
  -d '{ ... }'
```

Keys are issued per institution and scoped to it: you only ever see your own data. They do not expire unless rotated or revoked. A new key's raw value is shown **once**, at creation — store it immediately.

Institution admins manage keys at `GET /api-keys`, `POST /api-keys`, `POST /api-keys/{key_id}/revoke` and `POST /api-keys/{key_id}/rotate`.

## Bearer token

<Warning>
  Login is `application/x-www-form-urlencoded`, **not** JSON. Sending JSON returns `422`.
</Warning>

```bash
curl -X POST https://monitor.agregartech.com/api/v1/auth/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=you@example.com&password=yourpassword"
```

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer"
}
```

Then:

```bash
curl "https://monitor.agregartech.com/api/v1/transactions?page=1&page_size=20" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..."
```

Access tokens last **30 minutes**, refresh tokens **7 days**. On `401`, exchange the refresh token at `POST /auth/refresh` rather than logging in again.

## Roles

A token's role decides what it may do. An API key is not subject to roles — it is limited by the table above instead.

| Role | Can do |
|---|---|
| `CLIENT_ADMIN` | Everything below, plus users and API keys |
| `COMPLIANCE_OFFICER` | File STRs, manage cases, read everything |
| `SENIOR_ANALYST` | Work and assign cases, file STRs |
| `ANALYST` | Work assigned cases and the unassigned queue |
| `AUDITOR` | Read-only, including the audit trail |

`403 Permission denied` means your role lacks the permission; ask your institution admin. `401` means the credential itself was rejected — check you are using the right one for that endpoint.
