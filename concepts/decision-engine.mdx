## Decision flow

The decision engine runs after risk scoring and produces the final disposition for every transaction.

```
composite_risk_score
        │
        ▼
  Screening overrides ─ Sanctions hit → strictest thresholds
  (tighten, not force)  PEP hit → stricter thresholds
                        FATF high-risk → +transaction risk
        │
        ▼
  Threshold mapping
  ┌──────────────────────────────────────────┐
  │ 0–89   → ALLOW                           │
  │ 90–119 → FLAG                            │
  │ 120–149→ STEP_UP                         │
  │ 150–199→ HOLD                            │
  │ 200–300→ BLOCK                           │
  └──────────────────────────────────────────┘
        │
        ▼
  Post-decision actions
  ├── FLAG: create alert, notify via webhook
  ├── STEP_UP: call step-up verification service
  ├── HOLD: create alert, return HOLD decision
  └── BLOCK: create alert, return BLOCK decision (bank enforces)
```

---

## Override triggers

These checks run **before** threshold mapping. They don't hard-code a decision — they **tighten the thresholds** (and open the relevant case or report), so a lower score is enough to reach `HOLD` or `BLOCK`:

| Condition | Effect | Source |
|---|---|---|
| Sanctions hit | Strictest thresholds → typically `BLOCK`; SANCTIONS case opened | [Screening API](/compliance/sanctions) (`/aml/check`) |
| PEP hit | Stricter (PEP) thresholds; AML case opened | [Screening API](/compliance/sanctions) (`/aml/check`) |
| Adverse-media hit | Stricter thresholds | [Screening API](/compliance/sanctions) (`/aml/check`) |
| FATF / high-risk counterparty jurisdiction | Adds transaction-risk points | Jurisdiction config |
| High-value cash transaction | Stricter thresholds; CTR drafted | Jurisdiction CTR threshold |
| Travel Rule threshold exceeded | Travel Rule fields required | FATF R.16 config |

## Step-up verification

When a transaction scores in the `STEP_UP` range (120–149), the decision engine calls an external step-up verification service before releasing or holding the transaction:

| Variable | Purpose |
|---|---|
| `STEPUP_VERIFICATION_URL` | External step-up service endpoint |
| `STEPUP_VERIFICATION_API_KEY` | Auth key for that service |
| `STEPUP_VERIFICATION_TIMEOUT` | Maximum wait time (default 3s) |

If the step-up service is unreachable or times out, the transaction falls back to `HOLD`.

## Post-decision actions

### ALLOW
Transaction accepted and stored. No alert created.

### FLAG
- Alert created with `REVIEW` priority (priority is derived from the combined score — see below)
- Transaction stored and released
- Webhook fired
- Analyst queue updated

### STEP_UP
- External step-up call fired
- If verified → `ALLOW`
- If rejected or timeout → `HOLD`

### HOLD
- Alert created with `BATCH` priority (combined score 150–199)
- Transaction stored but held (not released to recipient)
- Webhook fired
- Case auto-created if the hold persists beyond 24h

### BLOCK
- Alert created with `IMMEDIATE` priority (combined score ≥ 200)
- The `BLOCK` decision is returned in the ingestion response; the transaction is recorded but not released — your core banking system enforces the block
- Webhook fired

<Note>
  **Alert priority** is derived from the combined score, independent of the decision label: `IMMEDIATE` at 200+, `BATCH` at 150–199, `REVIEW` at 90–149. There is no `MEDIUM` priority.
</Note>

## Configuring thresholds

View current jurisdiction thresholds:

```bash
curl https://monitor.agregartech.com/api/v1/jurisdictions/GHA \
  -H "X-API-Key: your_api_key_here"
```

Threshold changes go through four-eyes approval:

```bash
curl -X POST https://monitor.agregartech.com/api/v1/approvals \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJ..." \
  -d '{
    "action_type": "THRESHOLD_CHANGE",
    "payload": {
      "jurisdiction_code": "GHA",
      "changes": { "flag_threshold": 85, "hold_threshold": 145 }
    }
  }'
```

A second approver must call `POST /approvals/{id}/approve` before the change takes effect.
