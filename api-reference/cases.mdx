## Overview

A case groups one or more related alerts into a single investigation. Cases are the escalation path from an alert to a **Suspicious Transaction Report (STR)** or Currency Transaction Report (CTR). Once filed, the case is immutable and a goAML XML snapshot is captured.

Read endpoints require the `view_cases` permission; endpoints that create or change a case require `assign_cases` unless noted otherwise.

## Open a case

```bash
POST /api/v1/cases
```

```bash
curl -X POST https://monitor.agregartech.com/api/v1/cases \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "case_type": "AML",
    "title": "Suspected layering — 12 rapid transfers",
    "priority": "HIGH"
  }'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `case_type` | string | Yes | `AML`, `FRAUD`, or `SANCTIONS` |
| `title` | string | Yes | Short case label |
| `priority` | string | No | `HIGH`, `MEDIUM`, or `LOW` (default: `MEDIUM`) |
| `jurisdiction_id` | string | No | Jurisdiction code for goAML filing |

<Note>
  A case has no `alert_id` or `description` field. It opens empty, in `OPEN` status — link alerts afterward with `POST /cases/{case_id}/alerts` below.
</Note>

<ResponseExample>
```json

  "case_type": "AML",
  "status": "OPEN",
  "priority": "HIGH",
```

## Get case detail

```bash
GET /api/v1/cases/{case_id}
```

Returns the full case record — `case_type`, `status`, `priority`, `title`, `narrative`, `assigned_to`, `jurisdiction_id`, `due_date`, `resolution`, and timestamps. Use the sub-resource endpoints below for linked alerts, notes, and history.

<Note>
  L1 analysts only see cases their institution's case-access mode allows (none, their own, or all) — a case outside that scope returns `403`.
</Note>

## Case network graph

```bash
GET /api/v1/cases/{case_id}/graph
```

The link-analysis view for a case: `{nodes, edges}` spanning the case, its alerts, the subject customers, the devices those customers used, the SIM/handset IDs on those devices, and any other customers who share those devices (the ring). Node counts are capped so a busy device or large case doesn't produce an unusable graph.

<ResponseExample>
```json

  "nodes": [
    {"id": "case:9e1a3b5c-...", "type": "case", "label": "Suspected layering", "case_type": "AML", "status": "INVESTIGATING", "priority": "HIGH"},
    {"id": "alert:ALT-001234", "type": "alert", "label": "ALT-001234", "priority": "IMMEDIATE", "status": "INVESTIGATING", "risk_score": 112},
    {"id": "customer:CUST-001", "type": "customer", "label": "CUST-001", "in_case": true, "name": "J*** A***", "risk_level": "MEDIUM", "is_pep": false}
  ],
  "edges": [
    {"source": "case:9e1a3b5c-...", "target": "alert:ALT-001234", "type": "has_alert"},
```

## Update case status

```bash
PATCH /api/v1/cases/{case_id}/status
```

```bash
curl -X PATCH https://monitor.agregartech.com/api/v1/cases/9e1a3b5c-0000-0000-0000-000000000000/status \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{"to_status": "INVESTIGATING", "assigned_to": "7a2b1c3d-0000-0000-0000-000000000000", "notes": "Assigned for review"}'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `to_status` | string | Yes | Target status. Also accepted under the key `status`. |
| `assigned_to` | UUID | No | Set the assignee as part of the transition |
| `narrative` | string | No | Required by the SAR_DRAFTED transition |
| `resolution` | string | No | Required by the CLOSED transition |
| `notes` | string | No | Recorded on the status-history entry |

<Warning>
  `SAR_DRAFTED → SAR_FILED` cannot be done here — use `POST /cases/{case_id}/sar-filing` below.
</Warning>

<Note>
  L1 analysts (`close_alerts` only) may only transition a case to `CLOSED` or `ESCALATED`. Any other target status requires the `assign_cases` permission, or the call returns `403`.
</Note>

## Assign case

```bash
PATCH /api/v1/cases/{case_id}/assign
```

Reassigns a case without changing its status. Requires `assign_cases`.

```bash
curl -X PATCH https://monitor.agregartech.com/api/v1/cases/9e1a3b5c-0000-0000-0000-000000000000/assign \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{"assigned_to": "investigator-uuid", "notes": "Handing off — I am out next week"}'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `assigned_to` | UUID or `null` | No | New assignee. `null` unassigns the case. |
| `notes` | string | No | Recorded on the status-history entry |

<Note>
  Terminal cases (`CLOSED`, `SAR_FILED`) can't be reassigned — returns `409 Conflict`. Reassigning to the current assignee is also a `409`.
</Note>

## File SAR/STR

```bash
POST /api/v1/cases/{case_id}/sar-filing
```

Requests the `SAR_DRAFTED → SAR_FILED` transition via four-eyes approval. The case must already be in `SAR_DRAFTED` status (drafted with a narrative via `PATCH /status`). This call takes **no request body** — it creates a pending approval and returns immediately; it does not file anything itself.

```bash
curl -X POST https://monitor.agregartech.com/api/v1/cases/9e1a3b5c-0000-0000-0000-000000000000/sar-filing \
  -H "Authorization: Bearer eyJ..."
```

<ResponseExample>
```json
{
  "approval_id": "c2d3e4f5-0000-0000-0000-000000000000",
  "case_id": "9e1a3b5c-0000-0000-0000-000000000000"
}
```
</ResponseExample>

Returns `202 Accepted`. If the case isn't in `SAR_DRAFTED` status, this returns `409 Conflict`.

<Warning>
  Once the approval below is granted and the case reaches `SAR_FILED`, it becomes immutable and the goAML XML snapshot is captured. Amendments require opening a new supplementary case.
</Warning>

## Approve the SAR filing

```bash
POST /api/v1/approvals/{approval_id}/approve
```

This is the four-eyes step that actually completes the filing: a **different** user from the one who called `sar-filing` approves the pending request, which executes the `SAR_DRAFTED → SAR_FILED` transition. Requires the `approve_action` permission.

```bash
curl -X POST https://monitor.agregartech.com/api/v1/approvals/c2d3e4f5-0000-0000-0000-000000000000/approve \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{"notes": "Reviewed narrative and evidence — approved."}'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `notes` | string | No | Reviewer notes |

To reject the draft instead, call `POST /api/v1/approvals/{approval_id}/reject` with the same body shape.

## Request verification

```bash
POST /api/v1/cases/{case_id}/request-verification
```

Sends a KYC document-verification link for the case's subject customer (resolved from the case's first linked alert, unless `customer_id` is given) and links the verification back to this case. Requires `upload_evidence` or `assign_cases`.

```bash
curl -X POST https://monitor.agregartech.com/api/v1/cases/9e1a3b5c-0000-0000-0000-000000000000/request-verification \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{}'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `destination` | string | No | Email to send the verification link to. Defaults to the customer's stored contact. |
| `customer_id` | string | No | Needed only if the case has no linked alert to resolve the customer from |

<ResponseExample>
```json
{
  "status": "created",
  "verification_id": "VER-004522",
  "destination": "customer@example.com",
  "delivered": true,
  "message": "Verification link sent to customer@example.com."
}
```
</ResponseExample>

<Warning>
  Returns `422` if no customer can be resolved (no linked alert and no `customer_id`), and `422` if that customer has no stored contact and no `destination` is given.
</Warning>

## Case status lifecycle

```
OPEN          → ASSIGNED       (requires assigned_to)
              → INVESTIGATING  (requires assigned_to — skips the assignment step)
              → CLOSED         (requires resolution)
ASSIGNED      → IN_REVIEW
              → INVESTIGATING
              → CLOSED         (requires resolution)
IN_REVIEW     → INVESTIGATING
              → ESCALATED
              → SAR_DRAFTED    (requires narrative)
              → CLOSED         (requires resolution)
INVESTIGATING → ESCALATED
              → SAR_DRAFTED    (requires narrative)
              → CLOSED         (requires resolution)
ESCALATED     → SAR_DRAFTED    (requires narrative)
              → CLOSED         (requires resolution)
SAR_DRAFTED   → SAR_FILED      (four-eyes: POST /sar-filing, then POST /approvals/{id}/approve)
              → INVESTIGATING  (revert if the draft is rejected)
SAR_FILED     → CLOSED
CLOSED        → (terminal)
```

| Status | Description |
|---|---|
| `OPEN` | Case created, awaiting assignment |
| `ASSIGNED` | Assigned to an analyst, not yet actively reviewed |
| `IN_REVIEW` | Analyst has confirmed active review |
| `INVESTIGATING` | Analyst actively investigating |
| `ESCALATED` | Referred to a supervisor |
| `SAR_DRAFTED` | Narrative drafted, ready for the SAR filing request |
| `SAR_FILED` | Approved and submitted; immutable |
| `CLOSED` | Investigation complete |
