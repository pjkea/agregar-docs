## Overview

An alert is created automatically whenever a transaction decision is `FLAG`, `HOLD`, or `BLOCK`. Alerts are the primary analyst workflow — they link the transaction, triggered rules, the case (if opened), and the resolution.

---

## List alerts

```bash
GET /api/v1/alerts
```

### Query parameters

| Parameter | Type | Description |
|---|---|---|
| `status` | string | `OPEN`, `INVESTIGATING`, `CLOSED` |
| `priority` | string | `IMMEDIATE`, `BATCH`, `REVIEW` |
| `customer_id` | string | Filter by customer |
| `assigned_to` | string | Filter by assigned analyst |
| `start_date` | ISO 8601 | Alert created at or after |
| `end_date` | ISO 8601 | Alert created before |
| `page` | integer | Page number (default: 1) |
| `page_size` | integer | Results per page (default: 20, max: 100) |
| `sort_by` | string | `alert_timestamp`, `risk_score`, or `priority` (default: `alert_timestamp`) |
| `sort_order` | string | `asc` or `desc` (default: `desc`) |

<Note>
  A plain analyst only sees alerts assigned to them plus the unassigned pool. `assigned_to` filtering, and institution scoping, happen on top of whatever filters you pass.
</Note>

### Example

```bash
curl "https://monitor.agregartech.com/api/v1/alerts?status=OPEN&priority=IMMEDIATE" \
  -H "X-API-Key: your_api_key_here"
```

## Update alert

```bash
PATCH /api/v1/alerts/{alert_id}
```

Updates status, reassigns the alert, and/or appends a note in one call.

- **status**: `OPEN`, `INVESTIGATING`, or `CLOSED`
- **assigned_to**: analyst identifier. Requires the `assign_cases` permission — the same supervisory gate as `POST /assign` below.
- **notes**: if present, recorded as an investigation note on the alert.

```bash
curl -X PATCH https://monitor.agregartech.com/api/v1/alerts/ALT-001234 \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{"status": "INVESTIGATING"}'
```

<ResponseExample>
```json
{
  "success": true,
  "message": "Alert updated successfully",
  "alert_id": "ALT-001234",
  "updated_at": "2026-06-11T15:12:00Z"
}
```
</ResponseExample>

## Assign alert

```bash
POST /api/v1/alerts/{alert_id}/assign
```

Assigns the alert to an analyst. This is a supervisory action, distinct from setting `assigned_to` on the `PATCH` above — both go through the same `assign_cases` permission check, but this endpoint also runs the assignment through the investigation service (so it's recorded with an audit note). Requires `assign_cases` (held by `SYSTEM_ADMIN`, `COMPLIANCE_OFFICER`, or `SENIOR_ANALYST`).

```bash
curl -X POST https://monitor.agregartech.com/api/v1/alerts/ALT-001234/assign \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{"analyst_id": "analyst@institution.com", "notes": "Reassigning — you handled the related case last week."}'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `analyst_id` | string | Yes | Analyst to assign the alert to |
| `notes` | string | No | Optional note recorded with the assignment |

<ResponseExample>
```json
{
  "success": true,
  "message": "Alert assigned successfully",
  "alert_id": "ALT-001234",
  "updated_at": "2026-06-11T15:14:00Z"
}
```
</ResponseExample>

## Claim alert

```bash
POST /api/v1/alerts/{alert_id}/claim
```

Self-assigns an unassigned alert to the calling analyst. Requires `close_alerts` (held by `ANALYST` and above).

```bash
curl -X POST https://monitor.agregartech.com/api/v1/alerts/ALT-001234/claim \
  -H "Authorization: Bearer eyJ..."
```

<Note>
  Idempotent — claiming an alert you already own succeeds with `"Alert already claimed by you"`. Claiming an alert assigned to a different analyst returns `409 Conflict`.
</Note>

## Request verification

```bash
POST /api/v1/alerts/{alert_id}/request-verification
```

Sends a KYC document-verification link for the alert's customer, and links the verification back to this alert so the result feeds back into the investigation. Requires `upload_evidence` or `assign_cases`.

```bash
curl -X POST https://monitor.agregartech.com/api/v1/alerts/ALT-001234/request-verification \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{}'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `destination` | string | No | Email to send the verification link to. Defaults to the customer's stored contact. |

<ResponseExample>
```json
{
  "status": "created",
  "verification_id": "VER-004521",
  "destination": "customer@example.com",
  "delivered": true,
  "message": "Verification link sent to customer@example.com."
}
```
</ResponseExample>

<Warning>
  If the customer has no stored contact and no `destination` is given, this returns `422` with `"No contact on file for this customer — provide a destination email."` If an active verification already exists for the customer, `status` comes back `skipped_existing` and `verification_id` points at the existing one.
</Warning>

## Resolve alert

```bash
POST /api/v1/alerts/{alert_id}/resolve
```

Closes an alert with an analyst decision. Requires `close_alerts`.

```bash
curl -X POST https://monitor.agregartech.com/api/v1/alerts/ALT-001234/resolve \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "resolution": "LEGITIMATE",
    "resolution_notes": "Customer confirmed the activity; no further action.",
    "sar_filed": false
  }'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `resolution` | string | Yes | `FALSE_POSITIVE`, `LEGITIMATE`, `SAR_FILED`, or `RESTRICTED` |
| `resolution_notes` | string | Yes | Notes explaining the resolution |
| `sar_filed` | boolean | No | Whether a SAR was filed for this alert (default: `false`) |

### Resolution values

| Value | Description |
|---|---|
| `FALSE_POSITIVE` | Alert was incorrect; ML label recorded for retraining |
| `LEGITIMATE` | Activity reviewed and confirmed legitimate |
| `SAR_FILED` | A Suspicious Activity Report has been filed in connection with this alert |
| `RESTRICTED` | Account or activity restricted as a result of the investigation |

<Note>
  Every resolution feeds the XGBoost and River ARF self-learning pipeline. Resolution quality directly improves future model accuracy.
</Note>

## Escalate alert

```bash
POST /api/v1/alerts/{alert_id}/escalate
```

Atomically opens (or reuses) a case from the alert and escalates it to supervisor review, in one transaction: `OPEN → INVESTIGATING → ESCALATED`. Requires `close_alerts`.

```bash
curl -X POST https://monitor.agregartech.com/api/v1/alerts/ALT-001234/escalate \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "reason": "Pattern consistent with layering — needs supervisor review.",
    "assignee_id": "supervisor-uuid-here"
  }'
```

| Field | Type | Required | Description |
|---|---|:---:|---|
| `reason` | string | Yes | Why the alert is being escalated |
| `assignee_id` | string | No | Supervisor to assign the resulting case to |

<ResponseExample>
```json
{
  "case_id": "9e1a3b5c-0000-0000-0000-000000000000",
  "status": "ESCALATED",
  "title": "Escalated alert ALT-001234",
  "case_type": "AML",
  "institution_id": "a1b2c3d4-0000-0000-0000-000000000000",
  "jurisdiction_id": null,
  "assigned_to": "supervisor-uuid-here",
  "created_at": "2026-06-11T15:20:00Z",
  "updated_at": "2026-06-11T15:20:00Z"
}
```
</ResponseExample>

<Note>
  Safe to retry: if the alert is already linked to a case, that case is returned (and re-escalated, unless it's already in a terminal state).
</Note>
