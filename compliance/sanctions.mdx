## How screening works

At ingestion, every transaction is screened through the **Screening API** — a dedicated service (`POST /api/v1/aml/check`) that checks the customer and counterparty names against sanctions, PEP, and adverse-media sources and returns a status for each signal plus an `is_listed` flag:

| Signal | Result |
|---|---|
| **Sanctions** | A status per name: clear, potential match, or confirmed match |
| **PEP** | A status per name: clear, potential match, or confirmed match |
| **Adverse media** | Clear or hit |

A hit does **not** directly assign a risk score. Instead it **tightens the decision thresholds** for that transaction (see [Decision Engine](/concepts/decision-engine)): a sanctions hit applies the strictest thresholds — so the transaction typically lands on `BLOCK` — while a PEP or adverse-media hit applies stricter thresholds. Sanctions and PEP hits also open the matching case automatically.

<Note>
  A separate, local `rapidfuzz` three-pass matcher (MATCH ≥ 95 / REVIEW ≥ 80 / CLEAR below 80) powers **custom-watchlist** screening and the **USSD fast-path** sanctions gate. It is not the ingestion screening path described above — don't conflate the two.
</Note>

## What the client sees

Screening runs synchronously during ingestion, but a hit is **not** an HTTP rejection. Ingestion still returns `201 Created` — the request itself always succeeds. The verdict comes back as data, and your core banking system enforces it:

- **Synchronous** (`?process_immediately=true`, or once async processing completes) — the verdict fields are populated in the ingestion response.
- **Asynchronous** (default) — poll `GET /api/v1/transactions/{transaction_id}` or subscribe to the `TRANSACTION_SCORED` [webhook](/guides/webhooks).

```json
{
  "success": true,
  "transaction_id": "TXN-X9Z3Q1",
  "combined_risk_score": 240,
  "flagged": true,
  "alert_id": "ALT-00123",
  "processing_complete": true
}
```

The full decision label (`BLOCK`, `HOLD`, …) and screening detail live on the scored transaction — fetch it with `GET /api/v1/transactions/{transaction_id}`. HOLD matches also surface in the review queue below.

## Sanctions review queue

```bash
GET /api/v1/watchlists/screening-queue
```

Returns all transactions in `HOLD` state from sanctions matches awaiting manual review.

---

## Review a match

```bash
POST /api/v1/watchlists/screening-queue/{match_id}/review
```

```bash
curl -X POST https://monitor.agregartech.com/api/v1/watchlists/screening-queue/MATCH-000345/review \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "decision": "FALSE_POSITIVE",
    "notes": "Different person — customer born 1982 in Accra; SDN entry is a different individual."
  }'
```

| Decision | Effect |
|---|---|
| `CONFIRMED` | Transaction permanently blocked; SAR filed |
| `FALSE_POSITIVE` | Hold lifted; transaction released; customer note added |

## PEP screening

PEP records are screened by the same Screening API. A PEP hit applies stricter (PEP) decision thresholds and opens an AML case automatically. You can supplement screening with custom PEP entries in your own watchlist:

```bash
POST /api/v1/watchlists
Content-Type: application/json

{
  "name": "John Mensah Doe",
  "entity_type": "INDIVIDUAL",
  "category": "PEP",
  "reason": "Senior government official, Ministry of Finance",
  "jurisdiction": "GHA"
}
```

## Custom watchlists

```bash
POST   /api/v1/watchlists          # add entry
GET    /api/v1/watchlists          # list entries
DELETE /api/v1/watchlists/{id}     # remove entry
```

Custom entries are screened using the same fuzzy-match logic.

---

## List update schedule

Sanctions lists refresh daily at 02:00 UTC. Check last update time:

```bash
curl https://monitor.agregartech.com/api/v1/watchlists/list-status \
  -H "X-API-Key: your_api_key_here"
```

<Note>
  Screening adds approximately 15–30 ms to ingestion latency. The USSD fast-path (≤ 2s SLA) runs a lightweight sanctions gate first and defers full scoring to an async background task.
</Note>
