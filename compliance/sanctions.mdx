## What happens

Every transaction is screened against sanctions, PEP and adverse-information sources as part of ingestion — you do not need to call anything for this to happen. That automatic screening normally goes through a dedicated external screening service; if that service is unreachable, screening falls back to the same local name-matching engine documented below under [On-demand screening](#on-demand-screening).

| Signal | Source |
|---|---|
| **Sanctions** | OFAC, UN, EU and OpenSanctions |
| **PEP** | OpenSanctions politically-exposed-person records |
| **Adverse information** | OpenSanctions criminal, wanted and person-of-interest listings |

<Note>
  Adverse information means **structured listings** — criminal convictions, wanted notices, debarment — not press coverage. Someone written about in the media but not listed anywhere will not appear here. If your risk appetite requires news screening, that is a separate feed and worth raising with us.
</Note>

## How a hit affects the decision

A hit does **not** add points to the risk score. It **tightens the decision thresholds** for that transaction, which makes a `hold` or `block` far more likely at the same score:

| Hit | Effect |
|---|---|
| Sanctions (confirmed listing) | Strictest thresholds; floored to at least `hold`; a SANCTIONS case opens automatically |
| PEP | Stricter thresholds; an AML case opens automatically |
| Adverse information | Stricter thresholds |
| Screening unavailable (external service **and** local fallback both failed) | Floored to at least `hold`, with an `IMMEDIATE`-priority alert — a failed screening is never treated as a clear |

See [Scoring and decisions](/concepts/scoring).

## A hit is not an HTTP error

Ingestion still returns `201 Created`. The request succeeded; the verdict comes back as **data**, and your core banking system is what enforces it.

Scoring is asynchronous by default, so the verdict is not in the ingestion response. Get it either way:

- poll `GET /api/v1/transactions/{transaction_id}` (needs a Bearer token), or
- subscribe to the `TRANSACTION_SCORED` [webhook](/guides/webhooks).

```json
{
  "success": true,
  "transaction_id": "TXN-X9Z3Q1",
  "combined_risk_score": 240,
  "flagged": true,
  "alert_id": "ALT-00123",
  "processing_complete": true
}
```

## Name matching

Matching is fuzzy, because sanctions lists and your customer records rarely agree on spelling, transliteration or name order. Scores band as:

| Score | Outcome |
|---|---|
| ≥ 95 | Match — treat as confirmed |
| 80-94 | Review — an analyst decides |
| < 80 | Clear |

Expect false positives in the review band. That is deliberate: in screening, a missed match costs far more than an extra review.

## On-demand screening

You can also screen a name directly, outside the transaction pipeline — useful for KYC/onboarding checks before a customer transacts, or for sweeping an existing customer base against newly loaded lists. These call the same local name-matching engine that backs the automatic fallback above.

<Note>
  These endpoints require a Bearer token with the `manage_sanctions_lists` permission. API keys are not accepted.
</Note>

| Endpoint | Purpose |
|---|---|
| `POST /sanctions/screen` | Screen a single name |
| `POST /sanctions/screen/batch` | Screen up to 100 names in one call |
| `GET /sanctions/status` | Cache status — entries loaded, lists loaded, current thresholds |

```bash
curl -X POST https://monitor.agregartech.com/api/v1/sanctions/screen \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "John Smith",
    "nationality": "GH",
    "id_number": "G1234567",
    "limit_lists": ["OFAC_SDN"]
  }'
```

`nationality` (ISO 3166-1 alpha-2), `id_number` and `limit_lists` are optional. `limit_lists`, when set, restricts matching to those named lists only.

```json
{
  "query_name": "John Smith",
  "query_normalized": "john smith",
  "recommendation": "REVIEW",
  "highest_score": 87.5,
  "candidates": [
    {
      "list_name": "OFAC_SDN",
      "list_type": "SANCTIONS",
      "matched_name": "John Smyth",
      "entry_value": "SDN-00412",
      "score": 87.5,
      "match_type": "fuzzy",
      "entry_metadata": {}
    }
  ],
  "screened_lists": ["OFAC_SDN", "EU_SANCTIONS", "LOCAL_PEP_GHANA"],
  "total_names_checked": 48213,
  "screening_duration_ms": 12.4,
  "screened_at": "2026-11-16T10:02:11Z"
}
```

`recommendation` is `CLEAR`, `REVIEW` or `MATCH` — the same bands as the table above. `POST /sanctions/screen/batch` takes `{"names": [...]}` (max 100 entries, each shaped like the single-screen request) and returns a JSON array of results in the same shape, one per name.

```bash
curl https://monitor.agregartech.com/api/v1/sanctions/status \
  -H "Authorization: Bearer eyJ..."
```

```json
{
  "loaded": true,
  "total_name_entries": 48213,
  "loaded_lists": ["OFAC_SDN", "EU_SANCTIONS", "UN_SC", "LOCAL_PEP_GHANA"],
  "thresholds": {
    "match": 95.0,
    "review": 80.0
  }
}
```

## Custom watchlists

You can maintain your own lists alongside the global ones — internal blocklists, previously-reported subjects, or names your compliance team wants flagged.

| Endpoint | Purpose |
|---|---|
| `GET /watchlists` | List your watchlists |
| `GET /watchlists/{name}/entries` | Entries in one list |
| `POST /watchlists/{name}/entries` | Add an entry |
| `DELETE /watchlists/{name}/entries/{value}` | Remove an entry |

These require a Bearer token.
