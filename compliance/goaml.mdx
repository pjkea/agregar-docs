## Overview

The system generates **goAML-compliant XML** for both Suspicious Transaction Reports (STR) and Currency Transaction Reports (CTR). These can be submitted directly to the Ghana Financial Intelligence Centre (FIC) and supported neighbouring regulators.

---

## Filing workflow

```
Transaction flagged → Alert created → Case opened → Case reaches SAR_DRAFTED →
STR report drafted (POST /str-reports) → Four-eyes approval → Filed → goAML XML generated
```

### Step 1 — Case from alert

```bash
curl -X POST https://monitor.agregartech.com/api/v1/cases \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "case_type": "AML",
    "title": "Suspicious layering pattern",
    "priority": "HIGH",
    "jurisdiction_id": "GHA"
  }'
```

Link the triggering alert to the case:

```bash
curl -X POST https://monitor.agregartech.com/api/v1/cases/{case_id}/alerts \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{"alert_id": "ALT-001234"}'
```

The case then needs a narrative and a `PATCH /cases/{case_id}/status` transition to `SAR_DRAFTED` before an STR report can be filed against it. See [Cases](/api-reference/cases) for the full case status lifecycle.

### Step 2 — Draft the STR report

Once the case is in `SAR_DRAFTED` status, create the STR report that carries the actual filing data:

```bash
curl -X POST https://monitor.agregartech.com/api/v1/str-reports \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "case_id": "11111111-1111-1111-1111-111111111111",
    "subject_customer_id": "CUST-00981",
    "subject_name": "Jane Doe",
    "suspicious_activity_type": "STRUCTURING",
    "reporting_entity": "Example Bank Ltd",
    "total_amount": 185000.00,
    "currency": "GHS",
    "transaction_count": 12,
    "date_range_start": "2026-10-01T00:00:00Z",
    "date_range_end": "2026-10-02T23:59:59Z",
    "narrative": "Customer exhibited structuring behaviour consistent with layering...",
    "jurisdiction_id": "GHA"
  }'
```

Every field above is optional at the schema level except `case_id`, but `GET /str-reports/{id}/preview` reports `ready_for_filing: false` until the report has a subject (name or customer ID), a narrative, an activity type, a reporting entity, and a date range — fill those in before filing. Only one STR report may exist per case.

The report is created in `DRAFT` status. While it is `DRAFT`, update it with `PATCH /str-reports/{report_id}`, or discard it with `POST /str-reports/{report_id}/withdraw`.

### Step 3 — Request filing

```bash
curl -X POST https://monitor.agregartech.com/api/v1/str-reports/{report_id}/file \
  -H "Authorization: Bearer eyJ..."
```

This takes no body and only works on a `DRAFT` report. It creates a `PendingApproval` and returns `202 Accepted` with an `approval_id`:

```json
{
  "approval_id": "22222222-2222-2222-2222-222222222222",
  "report_id": "33333333-3333-3333-3333-333333333333",
  "status": "PENDING_APPROVAL",
  "message": "STR filing requested — awaiting four-eyes approval."
}
```

<Note>
  The case-level `POST /cases/{case_id}/sar-filing` endpoint (documented in [Cases](/api-reference/cases)) is an equivalent entry point: it also takes no body, requires the case to be in `SAR_DRAFTED`, and files the STR report linked to that case. Use whichever your workflow already has a handle on — a report ID or a case ID. Either path creates the same kind of `PendingApproval` and ends with the STR marked `FILED`.
</Note>

### Step 4 — Approve the filing

```bash
curl -X POST https://monitor.agregartech.com/api/v1/approvals/{approval_id}/approve \
  -H "Authorization: Bearer eyJ..."
```

A **different** user from the one who requested filing must approve — this is a four-eyes control. On approval, the STR report is marked `FILED`, `filing_reference` and `filed_at` are set, a goAML XML snapshot is captured, and — if the parent case was still in `SAR_DRAFTED` — the case advances to `SAR_FILED` too.

---

## STR report status

| Status | Meaning |
|---|---|
| `DRAFT` | Analyst is populating narrative and details. Editable via `PATCH`, discardable via `withdraw`. |
| `FILED` | Four-eyes approval executed; `filing_reference` and `filed_at` are set. Terminal. |
| `WITHDRAWN` | Report retracted before filing (e.g. the case was rejected). Terminal. |

`PATCH /str-reports/{id}` and `POST /str-reports/{id}/withdraw` both return `409 Conflict` once a report is `FILED` or already `WITHDRAWN`. `POST /str-reports/{id}/file` returns `409 Conflict` on anything other than `DRAFT`.

## Retrieve goAML XML

```bash
# STR XML
curl https://monitor.agregartech.com/api/v1/str-reports/{report_id}/goaml-xml \
  -H "X-API-Key: your_api_key_here"

# CTR XML
curl https://monitor.agregartech.com/api/v1/ctr-reports/{report_id}/goaml-xml \
  -H "X-API-Key: your_api_key_here"
```

<Warning>
  If you receive `409 goAML XML was not captured for this filing`, structured JSON data is still available via `GET /filings/{id}`. Only the XML snapshot is missing (filings created before Phase 6).
</Warning>

## CTR thresholds

| Jurisdiction | Cash CTR threshold | Default currency |
|---|---|---|
| Ghana (GHA) | GHS 50,000 | GHS |
| Nigeria (NGA) | NGN 5,000,000 | NGN |
| Kenya (KEN) | KES 1,000,000 | KES |

CTRs are auto-generated when a transaction amount meets or exceeds the jurisdiction's threshold — there is no analyst drafting step, and filing is mandatory. Several same-day transactions that individually stayed under the threshold but sum above it are also captured, as an aggregate CTR against the transaction that tipped the sum over the line.

---

## CTR report status

| Status | Meaning |
|---|---|
| `PENDING` | Auto-generated, awaiting filing. |
| `FILED` | Filed with the regulator; `filing_reference` and `filed_at` are set. Terminal. |
| `EXEMPT` | Marked exempt from filing (e.g. an interbank or internal transfer). Terminal. |

### Exempting a CTR

A PENDING CTR that should not be filed — an interbank transfer, for example — can be marked exempt instead:

```bash
curl -X POST https://monitor.agregartech.com/api/v1/ctr-reports/{report_id}/exempt \
  -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" \
  -d '{"reason": "Interbank settlement transfer"}'
```

`reason` is optional. This is also a four-eyes action: a `SYSTEM_ADMIN` caller executes it immediately and gets `200` back; every other role gets `202` with an `approval_id`, and a second user must approve via `POST /approvals/{approval_id}/approve` before the report moves to `EXEMPT`.

## Immutable filing snapshots

Once filed, a goAML XML snapshot is stored immutably alongside the filing record:

- The regulator receives exactly the same document that is on record
- Amendments generate a new filing rather than overwriting the original
- The full audit trail links alert → case → SAR → filing → XML

---

## Regulator access

The `/filings` family is a **read-only** dashboard over immutable filing snapshots — one snapshot is captured for every STR or CTR at the moment it is filed. It is separate from `/str-reports` and `/ctr-reports`, which institution users already use for the live filing workflow above.

Regulator institutions (`REGULATOR_VIEWER` role, or an API key belonging to a `REGULATOR` institution) see filings scoped to their own jurisdiction. Agregar platform users see every jurisdiction. Because a snapshot only exists once something is filed, there is no `status` filter — everything `/filings` returns is already filed.

```bash
curl "https://monitor.agregartech.com/api/v1/filings?report_type=STR&jurisdiction_code=GHA&filed_after=2026-10-01T00:00:00Z" \
  -H "X-API-Key: regulator_api_key"
```

| Param | Notes |
|---|---|
| `report_type` | `STR` or `CTR` |
| `jurisdiction_code` | Platform users only — regulator callers are always scoped to their own jurisdiction |
| `filed_after` / `filed_before` | ISO 8601 timestamps |
| `page` / `page_size` | `page_size` max 200, default 50 |

```bash
curl https://monitor.agregartech.com/api/v1/filings/{snapshot_id} \
  -H "X-API-Key: regulator_api_key"
```

Returns the full immutable snapshot, including `snapshot_data` and whether a goAML XML copy was captured (`has_goaml_xml`).

```bash
curl https://monitor.agregartech.com/api/v1/filings/{snapshot_id}/goaml \
  -H "X-API-Key: regulator_api_key"
```

Downloads the goAML XML exactly as generated at filing time — distinct from `GET /str-reports/{id}/goaml-xml` and `GET /ctr-reports/{id}/goaml-xml`, which regenerate from the live report. Returns `409` if no XML was captured for that filing (pre-Phase 6 records, or generation failed).

```bash
curl https://monitor.agregartech.com/api/v1/filings/analytics \
  -H "X-API-Key: regulator_api_key"
```

Jurisdiction-level aggregate counts: `total_str`, `total_ctr`, `recent_30d` (last 30 days by type), and `by_type`. `by_jurisdiction` is included for platform users and for a regulator caller not scoped to a single jurisdiction.

Sandbox/test-mode filings never appear in `/filings` for platform or regulator callers — they are excluded from every cross-institution view so test data can never reach a regulator dashboard.
